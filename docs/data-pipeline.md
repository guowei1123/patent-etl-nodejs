# 数据处理流程与原始数据包说明

## 数据处理流程

系统将数据处理拆分为 3 个独立的手动步骤，每个步骤需在批次详情页手动触发：

```
创建批次 → 下载 → 处理 → 导入
(pending)  (downloaded) (processed) (completed)
```

### 状态流转

| 状态          | 含义                                                      | 可执行的下一步 |
| ------------- | --------------------------------------------------------- | -------------- |
| `pending`     | 初始，未开始                                              | download       |
| `downloading` | 正在下载                                                  | —              |
| `downloaded`  | 下载完成                                                  | process        |
| `processing`  | 正在处理（外层解压 + CRC 校验 + 流式解析 XML + 上传附图） | —              |
| `processed`   | 处理完成（parsed.json 已生成）                            | import         |
| `importing`   | 正在导入                                                  | —              |
| `completed`   | 全部完成                                                  | —              |
| `failed`      | 失败（可通过"修复状态"重置后重试）                        | —              |

### 修复状态（sync/fix）

当批次状态异常时，可通过"修复状态"功能根据本地文件系统实际情况重置批次状态：

- 调用 `verifyDownloadedArchive` 验证本地文件完整性
- 完整性验证通过 → 提升到对应中间状态（`downloaded`/`processed`）
- 完整性验证失败 → 回退到 `pending`，提示重新下载

### 各步骤职责

**1. 下载 (download)**

- 从 CNIPA FTP 服务器下载原始数据到本地 `data/<batch_code>/`
- 下载文件类型包括：`.zip`（主卷）、`.z01`~`.z99`（分卷）、`.gz`、`.xml`
- 支持断点续传：已下载的文件（本地大小与远程一致）会被跳过，部分文件从断点续传
- **完整性检测 1（下载原始数据）**：下载完成后验证多卷 ZIP 文件齐全（主卷存在、分卷序号连续、分卷大小一致）
- 前置条件：批次必须设置 `ftp_folder`，否则拒绝执行
- 前置状态：`pending`
- 完成后状态：`downloaded`

**2. 处理 (process)**

- 三阶段流水线，合并了原"解压"和"解析"两步：
  - **第一阶段（外层解压）**：检测下载目录中的压缩文件，按基础名分组。对于分卷 ZIP（`.zip` + `.z01`~`.zNN`），先按序拼接为单文件（`.merged.zip`），再用 yauzl 解压。独立 ZIP 和 `.gz` 文件直接解压。合并产生的临时文件在解压完成后（含失败重试）自动清理。提取全部文件（内层 ZIP、CRC 文件、索引等）到 `extracted/` 目录。内层 ZIP 仍需写磁盘以进行 CRC 校验
  - **第二阶段（CRC 校验）**：校验每个内层 ZIP 的 CRC32（与 `*-CRC.TXT` 文件比对）及 ZIP 结构完整性
  - **第三阶段（流式解析与附图上传）**：使用 yauzl 的 `openReadStream` 流式读取内层 ZIP 中的 XML 和 JPG/JPEG 文件。XML 直接传入 `parsePatentXml` 解析，**XML 文件不落盘**；JPG/JPEG 按 XML 中解析出的专利号、kind 和摘要图文件名归属到对应专利，并上传到 OSS
- 附图 OSS object key 固定为 `patents/{batchCode}/{docNumber}/{originalFileName}`，bucket 保持私有
- 处理阶段默认上传附图；如设置 `PROCESS_UPLOAD_IMAGES=0`，处理阶段只生成 `parsed.json`，不会上传附图或生成图片元数据
- OSS 未配置或上传失败时，处理步骤失败并写入同步日志，避免数据库记录与对象存储不一致
- 上传前会检查 object 是否已存在，已存在则跳过上传但仍写入专利图片元数据；同一内层 ZIP 内相同图片 key 只处理一次，避免重复计数
- 图片上传进度会写入同步日志并通过状态接口返回 `process_progress`，包括当前内层 ZIP、解析 XML 数、图片总数、已上传、已跳过和失败数
- 如果 `extracted/` 已有内层 ZIP（手动解压的情况），跳过第一阶段直接进入后续阶段
- 结果写入 `data/<batch_code>/parsed.json` 作为中间数据。该文件包含专利主数据和附图元数据，但尚未写入数据库
- 前置状态：`downloaded`
- 完成后状态：`processed`

**3. 导入 (import)**

- 读取 `parsed.json`，分批（每批 100 条）插入 PostgreSQL
- 使用 upsert 策略（按 `doc_number + kind` 去重）
- 主表写入后同步写入结构化子表和 `cnipa.patent_image` 图片元数据；当 upsert 命中已有专利时，会删除并重写该专利的子表记录和图片记录
- 导入完成后，专利详情 API 返回 `images` 列表，前端通过 `/api/patent-images/{image_id}` 读取图片。后端代理从数据库校验图片存在后读取 OSS 并返回二进制图片，不向前端暴露 OSS key、bucket、密钥或签名 URL
- 完成后保留 `data/<batch_code>/` 临时文件，可在批次详情页手动确认后清理
- 前置状态：`processed`
- 完成后状态：`completed`

### 下一批次处理前检查

执行下一批次前建议确认：

- 当前批次已经进入 `completed` 或 `failed` 等终态；数据库中不存在 `downloading`、`processing`、`importing` 等运行中状态
- 本地开发服务 `http://localhost:3000` 可正常访问；如果端口仍有 Node 进程监听但 HTTP 连接失败，应先重启 dev server
- 大批次处理会在 process 阶段进行大量 OSS PUT/HEAD 请求，确认 OSS 配置和网络可用后再启动

## 原始压缩包结构

数据来源为 CNIPA（中国国家知识产权局）FTP 服务器上的分卷 ZIP 压缩包。以批次 `CN-PA-TXTS-10-B-20231003`（2023 年 10 月 3 日发明授权公告）为例：

### 外层分卷 ZIP（FTP 下载产物）

```
data/CN-PA-TXTS-10-B-20231003/
├── 20231003.zip       # 主卷 (~780 MB)
├── 20231003.z01       # 分卷 1 (~1 GB)
├── 20231003.z02       # 分卷 2 (~1 GB)
├── 20231003.z03       # 分卷 3 (~1 GB)
└── 20231003.z04       # 分卷 4 (~1 GB)
                        # 合计 ~5 GB
```

这 5 个文件组成一个分卷 ZIP 压缩包。处理阶段先将 `.z01` → `.z02` → ... → `.zip` 按序流式拼接为单文件 ZIP，再用 yauzl 解压。合并产生的临时文件在解压后自动清理。解压后产出 `extracted/` 目录中的内容。

### 外层解压后目录结构（处理阶段中间产物）

```
data/CN-PA-TXTS-10-B-20231003/extracted/
│
├── 20231003-1-001.ZIP         # 内层 ZIP 1 (~966 MB, 含 ~2000 件专利)
├── 20231003-1-001-CRC.TXT     # ZIP 1 的 CRC 校验值
├── 20231003-2-001.ZIP         # 内层 ZIP 2 (~1 GB)
├── 20231003-2-001-CRC.TXT
├── 20231003-3-001.ZIP         # 内层 ZIP 3 (~1.2 GB)
├── 20231003-3-001-CRC.TXT
├── 20231003-4-001.ZIP         # 内层 ZIP 4 (~1.1 GB)
├── 20231003-4-001-CRC.TXT
├── 20231003-5-001.ZIP         # 内层 ZIP 5 (~750 MB)
├── 20231003-5-001-CRC.TXT
│
├── 20231003-INDEX-001.TXT     # 文本索引：本批次所有专利文件路径清单
├── 20231003-INDEX-B-001.XML   # XML 索引：9503 件专利的摘要（申请号、公告号、日期）
└── INDEX-CN-20231003-B-001.XML # 完整索引：含每件专利的详细元数据 (~50 MB)
```

注意：**XML 专利文件不再写入磁盘**。处理阶段通过 yauzl 流式读取内层 ZIP 中的 XML 文件，直接在内存中解析。

### 内层 ZIP 内部结构

每个内层 ZIP 包含按专利组织的子目录：

```
20231003-1-001.ZIP/
└── 1/
    ├── CN102015000163325CN00001047518250BFULZH20231003CN00Q/
    │   ├── ...XML    ← 专利全文数据（流式读取，不落盘）
    │   ├── ...JPG    ← 专利附图（流式读取并上传 OSS）
    │   └── ...JPG
    ├── CN102015000338898CN00001063076150BFULZH20231003CN00F/
    │   ├── ...XML
    │   └── ...JPG
    └── ...                     # 每个内层 ZIP 约 1900~2000 件专利
```

5 个内层 ZIP 合计包含 **9503 件发明专利**。

### 各文件用途总结

| 文件                             | 用途                       | ETL 是否使用                                        |
| -------------------------------- | -------------------------- | --------------------------------------------------- |
| 外层分卷 ZIP（.zip/.z01~.z04）   | 传输打包，解压后即废弃     | 间接（解压步骤的输入）                              |
| 内层 ZIP（\*-001.ZIP）           | 按分片打包的专利数据       | **是**（流式读取 XML 和 JPG/JPEG）                  |
| CRC 文件（\*-CRC.TXT）           | 校验对应 ZIP 的下载完整性  | **是**（处理步骤自动验证）                          |
| 文本索引（\*-INDEX-001.TXT）     | 全部专利文件路径清单       | 否                                                  |
| 摘要索引（\*-INDEX-B-001.XML）   | 专利号、申请号、日期等摘要 | 否                                                  |
| 完整索引（INDEX-CN-\*.XML）      | 含详细元数据的完整索引     | 否                                                  |
| 专利 XML（内层 ZIP 中的 \*.XML） | 单件专利的全文结构化数据   | **是，ETL 核心输入**（流式读取，不落盘）            |
| 附图 JPG（内层 ZIP 中的 \*.JPG） | 专利说明书附图             | **是**（上传 OSS，元数据写入 `cnipa.patent_image`） |
